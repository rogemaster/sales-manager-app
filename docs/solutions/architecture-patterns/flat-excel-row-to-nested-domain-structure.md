# 1행 = 1레코드 파이프라인에 N:1 중첩 구조를 담을 때

## 문제

상품 대량등록 엑셀에 옵션을 넣어야 했다. 그런데 `Product.option`은 `OptionCombination[]`이고, 조합 하나마다 `values`·`quantity`·`skuCode`·`optionPrice` 4개 값을 갖는다. 색상 2개 × 사이즈 3개면 조합이 6개다.

**엑셀은 한 행이 상품 하나다.** 조합 6개의 값 24개를 한 행에 담을 자리가 없다.

같은 문제가 SKU에도 걸렸다. 사용자 요구는 "엑셀 템플릿에 SKU 컬럼 추가"였는데, `skuCode`는 `Product`가 아니라 `OptionCombination`의 필드다. **옵션 조합을 만들지 않으면 SKU를 저장할 자리 자체가 없어서**, 두 요구는 분리해서 처리할 수 없었다.

## 선택지와 판단

| 선택지 | 판단 |
|--------|------|
| 1상품 = N행 (조합당 1행) | 조합별 값을 전부 지정할 수 있다. 대신 `processExcelUpload` → `validateExcelData` → 미리보기가 전부 "1행 = 1레코드" 전제라 통째로 손봐야 한다 |
| 시트 2장 (상품 + 옵션조합, 코드로 연결) | 가장 깔끔하지만 `XLSX.utils.sheet_to_json(workbook.Sheets[SheetNames[0]])`로 첫 시트만 읽는 구조라 파서부터 바뀐다 |
| **1상품 = 1행, 옵션은 컬럼 인코딩** ← 채택 | 파이프라인 무변경. 대신 조합별 개별 값 지정을 포기한다 |

**핵심 판단:** 파이프라인 전체를 바꾸는 비용이, 조합별 개별 값을 엑셀에서 지정하는 편의보다 컸다. 개별 값이 필요하면 상품수정 화면에서 고치면 된다 — 그 화면은 이미 조합별 입력을 지원한다.

## 인코딩 방식 — 한 셀에 욱여넣지 않는다

`색상:블랙,화이트`처럼 한 셀에 인코딩하는 방식을 먼저 검토했다가 버렸다. **옵션값에 콜론이나 콤마가 들어가면 깨지고 이스케이프 규칙이 필요해진다.**

컬럼을 `옵션명1` / `옵션값1`로 나누면 그 문제가 사라지고, 화면의 입력 필드(옵션명 하나 + 콤마 구분 옵션값 하나)와 1:1로 대응한다. 컬럼이 늘어나는 건 비용이지만 파싱 규칙이 없어지는 값이 더 크다.

## 포기한 것을 명시적으로 남긴다

이 결정의 결과로 **아래는 구현되지 않은 게 아니라 구조상 불가능**하다.

- 조합별 개별 수량·SKU·추가가격 지정
- `optionPrice` 엑셀 입력 (조합마다 다른 값을 한 셀에 담을 수 없어 전부 `0`)

대신 일괄 규칙으로 채운다 — 수량은 총수량 컬럼 값을 모든 조합에 주입하고, SKU는 접두사 + 자동 순번이다.

**Why 이걸 문서로 남기는가:** 코드만 보면 "조합별 값을 못 넣는다"가 **빠뜨린 것**으로 읽힌다. 다음 라운드에서 "SKU를 조합마다 지정할 수 있게 하자"는 제안이 나오면, 그건 기능 추가가 아니라 **행 모델을 바꾸는 일**이고 파이프라인 전체가 딸려온다. 그 사실이 보이지 않으면 작은 개선처럼 착수했다가 범위가 폭발한다.

## 일괄 규칙은 화면의 기존 동작에서 가져온다

새 규칙을 발명하지 않았다. 화면에 이미 있는 버튼의 동작을 그대로 옮겼다.

| 엑셀 | 대응하는 화면 동작 |
|------|-------------------|
| 총수량 값을 모든 조합의 `quantity`에 주입 | `수량 일괄설정` 버튼 |
| `totalQuantity = 조합수 × 총수량` | 같은 버튼이 하는 재계산 |
| SKU 접두사 + `-001` 3자리 순번 | `SKU 일괄생성` 버튼 |

조합 생성 자체도 화면이 쓰는 `validateOptions`·`optionCombinations`(`util/Options.ts`)에 그대로 위임했다. **엑셀이 자기만의 조합 규칙을 갖게 하면 지금 맞춰놔도 나중에 갈린다.**

`totalQuantity` 재계산은 엑셀에 적은 값(100)과 저장되는 값(600)이 달라지는 부작용이 있는데도 채택했다. 100을 보존하면 조합 수량의 합(600)과 어긋난 채 저장되고, 그 상품을 수정 화면에서 열어 `수량확정`을 누르는 순간 600으로 바뀐다 — **저장 시점이 아니라 나중에 조용히 갈리는 쪽이 나쁘다.**

## 미리보기는 저장될 값을 보여줘야 한다

첫 구현에서 미리보기 총수량 컬럼이 엑셀 셀을 그대로 찍었다. 100이 보이고 600이 저장됐다. 그 화면은 "3단계: 데이터 확인 및 저장" — 놀람을 막는 게 유일한 임무인 화면이라 결함이다.

고칠 때 **미리보기가 자기 계산식을 갖게 하지 않았다.** 계산을 `resolveTotalQuantity`로 뽑아 전략과 미리보기가 같은 함수를 부르게 하고, 두 경로가 갈리면 실패하는 테스트를 걸었다:

```ts
expect(resolveExcelTotalQuantity(row)).toBe(product.totalQuantity);
```

이 테스트는 **옵션이 있는 행**을 써야 한다. 옵션 없는 행으로 비교하면 양쪽 다 총수량을 그대로 돌려줘 통과하지만 아무것도 지키지 못한다.

## 컬럼명을 아는 지점은 하나여야 한다

전략(저장)과 미리보기(표시)가 각자 `'옵션명1'` 같은 리터럴로 셀을 읽고 있었다. 컬럼명을 바꾸면 전략 쪽은 테스트가 잡지만 **미리보기는 커버리지가 없어 조용히 빈칸이 된다.**

`toExcelOptionPairs(row)` 하나로 모았다. 실제로 그 직후 사용자가 컬럼명을 `옵션1명` → `옵션명1`로 바꿨고, 읽는 코드는 한 곳만 고치면 됐다.
