# 소비 화면이 데이터 모델을 결정한다 — 화면을 만들기 전 확정한 모델은 뒤집힌다

## Context

쇼핑몰 등록 기능을 세 라운드로 나눠 만들었다.

| 라운드 | 산출물 | 데이터 모델 결정 |
|--------|--------|-----------------|
| PR #35 | 전송 액션 UI | `Product.registeredMalls`에 등록 이력을 **append** |
| PR #36 | 전송 결과 영속화 | 이력이 아니라 현재 상태다 → 조합당 1건 **upsert**로 전환 |
| PR #37 | 연동 상품 목록 화면 | 독립 엔티티 + **스냅샷 보유**, 중복 연동 허용 → upsert 폐기 |

두 번의 라운드에서 모델이 연속으로 뒤집혔다. 매번 이유는 같았다 — **그 데이터를 실제로 보여주고 다루는 화면이 아직 없었기 때문**이다.

PR #36이 append를 upsert로 바꾼 근거는 "다음 라운드 화면에서 같은 조합이 두 줄로 쌓이면 이상하다"였다. 화면을 상상해서 내린 결정이었고, 그 방향 자체는 맞았다.

그런데 실제로 화면을 설계하며 사용자에게 물으니 요구사항이 이랬다.

> 오리지널 상품 데이터를 수정해도 `naver-A-상품`, `kakao-A-상품`은 수정되지 않는다. 연동된 데이터의 수정은 각자의 쇼핑몰 데이터를 수정해서 전송한다.

> 1개의 마스터 상품을 동일한 쇼핑몰에 여러 번 중복 전송할 수 있다. 각기 다른 쇼핑몰ID를 가진 여러 데이터가 생성된다.

`registeredMalls`는 상태 메타데이터(`status`, `registeredAt`, `externalId`)만 갖고 있어 **상품 값의 사본을 담을 자리가 없었고**, upsert(조합당 1건) 전제는 중복 전송 허용과 정면으로 충돌했다. 두 결정 모두 폐기하고 독립 엔티티로 전환했다.

## Root Cause

**"수정"이라는 단어가 무엇을 수정하는지는 화면을 그리기 전까지 결정되지 않는다.**

선행 라운드들은 연동 데이터를 "상품에 딸린 등록 상태"로 봤다. 이 관점에서 수정이란 상품을 고치고 다시 보내는 것이다. 그러면 사본은 필요 없다.

실제 도메인은 연동 데이터를 **외부 쇼핑몰에 올라간 별개의 상품**으로 본다. 네이버에 올린 A와 카카오에 올린 A는 각각 따로 가격을 바꾸고 따로 전송한다. 이 관점에서는 사본이 필수다.

두 관점의 차이는 저장 구조가 아니라 **사용자가 그 데이터로 무엇을 하느냐**에서 나온다. 그건 화면 요구사항을 물어봐야 알 수 있다.

## Guidance

**화면 없이 데이터 구조를 확정해야 한다면, 확정의 강도를 낮춘다.**

- 그 라운드에서 실제로 필요한 최소 필드만 넣는다. "나중에 쓸 것 같은" 구조를 미리 만들지 않는다 (YAGNI).
- 스펙 문서에 **어떤 화면 가정 위에서 내린 결정인지** 명시한다. 가정이 틀리면 뒤집힌다는 신호가 된다.
- 뒤집을 때는 **선행 결정을 남겨두지 말고 지운다.** 같은 사실이 두 곳에 저장되면 반드시 어긋난다.

**뒤집은 뒤에는 선행 라운드의 문서도 정리한다.** 이 프로젝트는 `docs/solutions/`를 "관련 기능 구현 전에 읽는" 인덱스로 쓰는데, 폐기된 결론이 `applies_when` 트리거를 단 채 남아 있으면 없는 것보다 나쁘다. 실제로 이번 라운드는 두 문서에 `superseded_by`와 안내 문단을 추가했고, **본문의 추론 과정은 지우지 않았다** — 결론은 뒤집혔어도 "소비 화면이 모델을 결정한다"는 추론 자체는 여전히 유효하기 때문이다.

## Why This Matters

- 라운드를 잘게 나누는 것 자체는 옳았다. 문제는 **저장 구조를 먼저 확정하고 화면을 나중에** 배치한 순서다. 반대 순서(화면 요구사항 → 저장 구조)였다면 두 번의 전환이 없었다.
- 다만 전환 비용은 실제로 크지 않았다 — 데이터가 mock이고 소비처가 없었기 때문이다. **소비처가 없을 때 뒤집는 것이 가장 싸다.** 화면이 생긴 뒤였다면 마이그레이션이 필요했다.
- 이 프로젝트의 `.claude/rules/domain-design.md`에는 몰이 3개 이상 되면 `MallAttributesMap` 파생 구조로 전환을 검토한다는 항목이 있고, 미루는 이유로 "n=2로 일반화하면 3번째의 실제 구조가 다를 때 다시 손봐야 한다"를 든다. **같은 원칙이다.**

## When to Apply

- "일단 데이터만 저장하고 화면은 다음에" 식으로 라운드를 나눌 때 — 저장 구조를 최소한으로 잡고, 화면 라운드에서 확정할 것을 명시
- 브레인스토밍에서 "수정", "관리", "처리" 같은 동사가 나올 때 — **무엇을 대상으로 하는지** 구체적으로 물을 것. 이번에도 그 질문이 모델 전체를 결정했다
- 선행 라운드의 결정을 뒤집을 때 — 코드뿐 아니라 그 결정을 기록한 문서까지 함께 정리
